## The finding that shapes this slice

The owner asked how a *dated occurrence's* reserved amount should be stated. Their ruling (**D-013**, verbatim in
the decisions file) permits either a Meridian-side user allocation or an even split of the set-aside total across
commitments, and states they do **not** know how Crew allocates per bill inside the single reserve bucket.

But Crew **does** report a per-bill figure, and we already store it. Do not rebuild what exists:

- `meridian/providers/crewwork.py::_collect_commitment_candidates` (~line 155) reads each bill's
  `reservedAmount` through `_cents_to_dollars_or_none` into `CommitmentCandidate.funded_amount` — nullable on
  purpose, so "Crew did not report it" stays distinct from "Crew reported zero" (the C01 rule pinned by
  `tests/meridian/test_reserve_integrity.py`).
- `commitments.funded_amount` is therefore already the observed per-bill reserved amount.
- **The dial ignores it for bills.** `meridian/services/dial.py::_commitment_events` BILL branch (~line 140)
  hardcodes `"fundingStatus": "unknown"` and `"reserved": None`. The GOAL branch in the same function already
  computes reserved / partial / unfunded plus an exact shortfall — that is the vocabulary to reuse.

So the order of precedence is: **observed per-bill figure → labelled even-split fallback → unknown.** The
even split is a fallback, not the mechanism.

## The bounded slice: OS-048b

**Display decision (owner-confirmed direction, "easiest to understand"):** the funding figure appears on
**exactly one date — the earliest occurrence within the horizon**. Later occurrences of the same bill stay
plain. The *source name* from OS-048a stays on every row, because identity is a stable fact about the bill and
implies no money. Rationale: the app's own headline is "Every dollar has a next job"; repeating a reserve across
four future rent rows reads as four times the money and is the misreading D-010 exists to prevent. Precedent:
the owner already objected to a status word sitting under a Paycheck amount.

Copy for the next occurrence only:

- covered → `Next due Oct 1 · $1,500 of $1,500 set aside`
- partial → `Next due Oct 1 · $1,200 of $1,500 set aside — $300 short`
- nothing set aside → `Next due Oct 1 · $1,500 — not yet set aside`
- derived fallback → the same line plus `(split evenly across this reserve — Meridian estimate)`
- nothing known → keep the existing honest `Funding unknown`

The evidence ticket carries the bill-level detail: "Set aside for this bill: $1,500 · observed from Crew ·
<date>" or "Meridian estimate, split across 3 bills". The centre status and the accessibility label follow the
same rule.

**Files to touch (expected):** `meridian/services/dial.py` (BILL branch + a per-reserve bill count for the
fallback), `static/js/meridian/dial.js` (normalise the new fields; render the four states; ticket row),
`tests/meridian/services/test_dial_funding_source.py` and/or a new focused test file,
`tests/meridian/test_dial_js.py`, plus status/coordination/claims/task records. A migration is **not** expected

**Payload changes should stay additive and self-describing:** a basis field (observed / derived / unknown) and
the derived divisor, so the UI can never present a derivation as an observation. Do not reuse `fundingStatus`
for the fallback without saying which basis produced it.

**Tests to write first (failing, then green):**

2. A derived figure is labelled and carries its basis/divisor; it is never attributed to Crew.
3. Unreported (NULL) is not treated as zero; reported zero reads "not yet set aside", not "unknown".
4. reserved > amount does not produce a negative shortfall; equal produces "covered".
5. Only the earliest occurrence in the horizon carries the status; a second occurrence in the same horizon does
   not.
6. The same reserve total is never multiplied by the number of future dates (the D-010 rule).
7. Multi-plan ambiguity and missing membership still resolve exactly as OS-048a pinned them.
8. The JS helper is executed under Node (not grepped) for all four states, including the derived label.
