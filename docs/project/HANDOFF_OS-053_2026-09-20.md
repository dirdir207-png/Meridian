## 2. The slice: the defect, verified by reading the code **[E]**

Two functions implement the same provider read, and only one of them runs in production.

**`meridian/sync.py:152` — `sync_providers` (plural): no production caller.** Called only by its own definition
and by tests. Inside, the candidate loop creates commitments with:

```python
recurrence=candidate.recurrence or "one_time",     # sync.py:~197
```

**`meridian/live.py` — `sync_live_crew`: the production path.** It calls `sync_provider` (**singular**), which
persists accounts and transactions but **not** the snapshot's commitment candidates, and then **re-implements the
candidate-to-commitment loop itself** at `live.py:63-89`:

```python
recurrence=candidate.recurrence or "monthly",      # live.py:~71
```

**They have already diverged, and the divergence has two halves:**

1. **On create**, the same frequency-less candidate stores `monthly` through production and `one_time` through the
   unused copy.
2. **On update**, they differ again — `live.py` preserves what is known
   (`due_date=candidate.due_date or existing.due_date`, `recurrence=candidate.recurrence or existing.recurrence`),
   which is the safer shape, and `sync.py` does not necessarily match it. **Read both update branches yourself
   before concluding — this document verified the create branches directly and only partially the update ones.**

**Risk is growing.** Three fields are now copied into **both** loops — the recurrence default, `bill_reserve_id`,
and `reserved_amount_reported` — so **every newly observed field doubles the chance of a silent divergence.**
OS-048b added a test pinning the two paths equal **on the reserve facts**, which converted this from an unverified
duplication into a *checked* one. **The recurrence divergence remains deliberate and untested against
production.**

## 3. Why this matters more than a "normal priority" tidy-up suggests

The owner's stated north star — roadmap **Track I.5**, ledger **OS-063** — is: *given an unforeseen cost and a
goal, "look at the foreseeable future and make any budget/bill/autopilot adjustments necessary."* **That
foreseeable future is built out of these commitment rows.** A recurrence value that is fabricated rather than
reported does not merely mis-render a label; it invents obligations (or erases them) in the very forecast the
whole capability reasons over.

And there is a constitutional problem, independent of which default is "right":

> **`candidate.recurrence or "monthly"` converts "Crew did not report a frequency" into the assertion "monthly".**

That is the absence-as-assertion error the project's **C01 rule** forbids everywhere else — *an unreported field
must never clear or fabricate a value; `None` means "the read did not report", never "zero"*. Here, two copies of
the same code make **two different assertions about the same silence**. Whatever is decided, the decision must be
made **explicitly** rather than inherited from an `or` default.

## 5. The decision this slice must make (owner-visible)

**The only contested part was answered by the owner on 2026-09-20 — "There is always a frequency" — so this is now
a REFACTOR, not a behaviour change.** No stored value changes for any real bill: no migration, no backfill, and no
semantics to renegotiate. Three shapes:

| Option | What it means | Cost |
|---|---|---|
| **A — unify on the shared mapping** | Production adopts one implementation's semantics | Nearly free now: no real candidate is affected, since none arrives frequency-less |
| **B — one path only** | Delete the duplicate; make `sync_providers` delegate to the shared function or remove it | Cleanest; touches a public-ish symbol (check callers/tests first) |
| **C — keep both, pin them equal** | A test asserts the two produce identical rows | Cheapest, but preserves the duplication that has already diverged |

**Recommended: B, with C's test as a safety net during the transition** — one mapping function, both entry points
calling it, and a test that fails if they diverge again. Unifying the two fallbacks into **one documented,
observable** fallback is the part that actually matters; which string it holds is nearly academic, because nothing
reaches it.

**And do not open the C01 question here.** Storing "unreported" as unreported would be the more principled design,
but it is a **schema change for a case that does not occur** — speculative infrastructure, out of scope for this
slice. C01 still binds for fields that genuinely can be absent (see §7). If the owner ever wants the principled
form, it belongs with a field that can really be missing.

## 7. Safety analysis

- **Production write path changes** → any behaviour change must be deliberate, tested, and documented as a
  behaviour change, never slipped in as a refactor.
- **C01 absence discipline** binds: an unreported field must never clear a known value, and `None` never means
  zero. A test must pin the distinction, not just the value.
- **No financial mutation** is involved in the analysis at all, which is why this is a safe slice to pick up.
- If a migration is needed: **never edit a shipped one** (it freezes every database that applied it and 503s
  every repository read). Register the new one in **four** places: the `.sql` file,
  `docs/project/shipped-migrations.json` (sha256 **and** `migration_count`), `_LATER_MIGRATIONS` in
  `tests/meridian/test_migrations.py`, and the exact applied-version pair list in that same test file.

- **The preview is a child of an agent shell and dies with it.** PID `92126` may be gone by the time you read
  this. The durable fix is the owner's Desktop launcher — `~/Desktop/Meridian Preview.command`, **installed and
  working** as of this handoff. Tell the owner to use it; never rely on an agent-started preview.
- **A shipped script that cannot run is a shipped script that does not work** (`8c1145f`).
  `scripts/install_desktop_shortcut.command` was committed `100644` and sat on disk as `-rw-------`, so Finder
  refused it with *"you do not have appropriate access privileges"* and the owner could not install the launcher
  at all. **Verified as existing ≠ verified as running.** Two lessons: (1) when you ship an executable, check the
  **exec bit in the working tree AND in git** (`git ls-files -s` → `100755`) — a fresh clone takes its modes from
  git, so a filesystem-only `chmod` leaves the bug in the repo; (2) `tests/test_launcher_scripts.py` now pins this
  for `scripts/*.command` and `*.sh`, and the test was **falsified before being trusted** (`chmod 644` → it
  fails). If you add another launcher, that test covers it.
- **Migration immutability** — see §7. This is the single most expensive mistake available here.
- **Shell hazards.** Long multi-line text through heredocs **silently loses characters**; a nested-heredoc
  `bash -c` once **timed out at 300 s and reset the shell, which swept the running preview**. Use the file tools
  for Markdown/JSON. Multi-line `git commit -F -` heredocs are reliable.
- **Editing docs: lines wrap.** A line you copy from `grep` may be **half a sentence**; read the file and copy
  exact text. `edit` requires an exact match — em dashes and typographic quotes are real mismatch causes. Prefer
  short **ASCII-only anchors**, then re-read to confirm.
- **`cadence` is legacy; `recurrence` is live** (§4, correction 1).
- **Admission gates.** Mutations are refused after `head-moved`, `constraints-changed`, or `re-entry-required`.
  Do one read-only step and the next mutation revalidates automatically. Every edit to a **governing doc**
  (roadmap, `MERIDIAN_DECISIONS.md`, `AGENTS.md`) invalidates admission again — **batch those edits**.
- **`read_image` is unavailable in this lane**, and `modlens_read_image` hallucinated. Verify layout numerically.
- **Never log credentials** (no tokens, cookies, OTPs, API keys) and **never assert causation** — state what was
  observed, not who caused it (§13).
