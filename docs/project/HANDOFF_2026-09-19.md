## The standing safety constitution (do not treat as optional)

Agents may observe, explain, simulate, propose, investigate, forecast, draft, test. **Only a
constrained executor may mutate financial state.** Never auto-retry a financial mutation; never
transfer externally and autonomously; never bypass proposal → approval → execution → provider
verification; never expand authority as a side effect of a feature. Treat an uncertain write as
unknown until a readback verifies it. Never present stale data as current, a forecast as fact, a
simulation as a real balance, or a recommendation as permission. Keep actual and simulated data
isolated and preserve provenance and timestamps. Report confidence and assumptions explicitly.

**The expected-income rule, as approved by the owner**: aggregate when there is enough data,
else the value of the last known source. Implemented in
`meridian/paycheck.py::resolve_expected_paycheck`, resolved **within the current income channel**
(never across a retired one) with the threshold `paycheck_learning._MIN_OCCURRENCES = 3`.

**A known deviation, deliberately made**: an observed fallback requires the channel to have

before the fix. The consequence: the **first** paycheck of a new job is a single observation and
therefore not yet usable as the default. Closing that needs an explicit designation of which
source is the paycheck rather than an inference from recency.

### 1. `OS-050` — the paycheck must resolve to a Crew record

Owner directive, verbatim: *"Right, it SHOULD be a crew record though, the paycheck"*. So the
current `Source: manual` stamp is **interim and not an acceptable destination**: the expected
paycheck must resolve to the Crew **bill-reserve funding plan**, and the stamp must read the
plan's name (e.g. "Veterans Home") because that is the record that actually pays it. The owner
confirmed the income source **is** the funding plan.

Priority order of the resolved amount:

1. the Crew funding plan — `{name, amount, frequency, frequencyInterval, anchorDate, billReserveId}`
2. Meridian's aggregate of ≥3 observed paychecks of the current channel — **labelled as Meridian's
   derivation**, because the owner's own framing puts aggregation there: *"The only deviation for
   Meridian is most likely the aggregation, I'm not sure if crew also does that naturally"*
3. the last observed value of a channel that has RECURRED
4. the locally configured figure — "manual", honest but interim

**How to ingest it — verified, do not rediscover:** the snapshot is fetched fresh per sync
(`meridian/live.py::capture_crew_snapshot`, wrapped by `CrewWorkSnapshotAdapter`) and is **not**
cached on disk, so the plans must be **persisted during sync**. `readback_funding_plans()` already
parses `expenses…accounts[].billReserve.fundingPlans[]` and returns each plan with its parent
`billReserveId`. `fundingPlans` is already a declared connector readback field
(`docs/project/CONNECTOR_READBACK_FIELDS_PATCH.md`), so **no connector change is needed** — only
persistence, identity and resolution. The write side already exists and is readback-verified
(`create`/`update`/`delete_crew_paycheck_funding_plan`).

Two-way sync is also required: setting a cadence in Meridian must set the income source in Crew,
Crew must populate it back, and **deletes must be symmetric**. The owner expects the value to be
stable unless they change jobs. Any cadence write is a **provider write** and must ride the
existing pipeline.

### 2. `OS-051` — make the learning governable and resettable

Owner, verbatim: *"you can implement learn check, but starting at yesterday. There needs to be a
nested owner operable setting to reset the learning. If I change jobs and have a different pay
rate, or at a different cadence, weekly vs bi weekly for instance, I shouldnt be including the
learned pay from previous positions"* … *"so it needs to be governable and resettable if
needed"*.

Constraints: a learning **floor** so only observations on or after it count; a **nested**
owner-operable control inside the income area (not top-level); a reset that deletes **no financial
records**, only changing which observations Meridian aggregates; persisted across restarts. Note
this is **independent** of the channel rule already shipped — the channel rule separates two live
sources, the floor rule separates this job from the last one. Both must hold.
