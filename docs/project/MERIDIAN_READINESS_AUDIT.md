# Meridian readiness audit and build preparation

September 13, 2026. This is an evidence-backed readiness review, not a release certificate. It supplements the execution gameplan and the single roadmap. Application baseline: `f1e4d0a6c9d48767a9795cc03bb00bfc8bd8dfe2`; Harness baseline: `a834868c143f4a896840b8d08a7777df1b899f13`. Earlier receipts retain their original source identities. No live data, credentials, banking operations, installed preset changes, service restart, deployment or live acceptance occurred.

## Judgment

Keep the vision and roadmap. Strengthen execution with demonstrated contracts before expanding features. The code has substantial useful substrate, but a module or passing isolated unit test does not establish an operating financial system. The most important next work is financial write verification and authority coverage, followed by a canonical observation/event stream shared by Today, forecasts and scenarios. The original concept composition and prominent safe-to-spend remain product acceptance requirements, not optional polish.

The new `CONCEPT_COVERAGE.md` and `MERIDIAN_IMPLEMENTATION_PLAN.md` already supply breadth across the 22 concepts; another wholesale rewrite would create competing authorities. Use this report to sharpen their acceptance gates. Implementation details for later concepts remain proposals requiring their own bounded specifications. Proper execution can substantially advance Meridian; neither this audit nor any roadmap can guarantee the complete vision without owner evaluation of the resulting product.

## Install and run order

This is a reproducible preparation order for the current repositories, not an instruction to upgrade everything. Do not replace a working global runtime to satisfy one project.

1. **Recover context and ownership first.** Read repository `AGENTS.md`, document index, current status, decisions, roadmap, this report and the selected slice. Inspect branch/dirty paths and both claim files. Preserve unrelated changes and unique refs. Do not mix the separate SimpleCrew/Chime trees into this build.
2. **Application Python environment.** Use Python 3.11 in the existing `.venv311`, or create a new project-local environment if absent. Install `requirements.txt` then `requirements-dev.txt` into that environment. Run `python -m pip check`. Observed local Python: 3.11.16; dependency check passed. Dev tools include pytest, Ruff, Playwright and pip-audit. Do not use a production-only runner for browser testing.
3. **Browser binaries.** With the same Python interpreter, run `python -m playwright install chromium webkit` when absent. They are already available on this host. Linux browser containers additionally need the matching browser system dependencies. Test both engines; Chromium alone is insufficient for the owner's iPhone layout.
4. **Git and Docker.** Git is required inside the test image because guardrail tests create disposable Git repositories. Docker is installed and was used successfully. The readiness Dockerfile installs Git and Python dependencies; it intentionally adds dev dependencies that the production image does not contain.
5. **Harness Node toolchain.** Current checkout declares Node `^22.19.0 || >=24.0.0` and `pnpm@11.7.0`. Observed Node 24.20.0 satisfies that range; observed global pnpm 12.3.4 differs. Select the declared pnpm per project before a future dependency install, and use `pnpm install --frozen-lockfile`. Do not add legacy runtime packages blindly or edit `node_modules`; inspect dependency ownership first. No Harness install was needed for this audit.
6. **Harness verification before activation.** Run the selected keyless tests, then the dedicated custom-preset H0 tests. For actual Harness source changes, use the checkout's complete build and its 4 GB host TypeScript command (`node --max-old-space-size=4096 ./node_modules/typescript/bin/tsc -b tsconfig.host.json`), plus affected client/build checks. This audit did not rebuild or restart the running Harness.
7. **Application baseline before a slice.** Run the isolated non-browser suite and relevant browser tests, record all skips/failures, then reproduce the slice's failing acceptance case. Fake provider responses must cover missing/partial/stale states. Do not introduce credentials to satisfy tests.
8. **Install custom preset only after its acceptance gate.** Preserve a reviewed prior preset, stage the candidate separately, prove effective system prompt, plan restrictions, compaction re-entry and denied filesystem/tool operations, then obtain the already-required owner activation approval. Test the candidate before touching the installed preset. Repository guardrails do not substitute for runtime enforcement.
9. **Deliver one vertical slice.** Claim → red acceptance case → minimal implementation → targeted checks → review → evidence/status → exact-path commit. Clear ownership overlaps before writing. Do not use an agent council to substitute for a missing contract.
10. **Release separately.** Matched source/data backup, isolated restore verification, actual production-entry-point test, visual acceptance, reviewed deployment and owner-approved live acceptance. Never infer these from the test-image success.

## Restore rehearsal and remaining production proof

The rehearsal uses a generated SQLite database and encrypted synthetic evidence. It seeds an accepted but unverified action, takes an online SQLite backup while committed WAL data exists, copies only generated evidence, damages original state, tests a failing migration transaction, rejects an altered backup and a wrong key, and restores into a separate marked directory. A **fresh Python process** then checks the account, non-retryable pending action, decrypted evidence and authenticated Today/Accounts/evidence routes. All 21 migrations apply. Temporary data is deleted after the test; receipts remain.

This proves the tested synthetic recovery path, including the application's current DB-derived evidence key. It does not prove recovery of the owner's real backup, macOS Keychain/broker credentials, another image version, interrupted external transfers, a remote host or physical-device Safari. Production rehearsal must use an owner-controlled protected backup, a matched runtime/config/key inventory, isolation from provider writes, explicit reconciliation of pending actions and a measured recovery time/data-loss window. A successful restore must never automatically replay unresolved operations.

To repeat safely, use the helper's `prepare-context` command with a **new** output path, build using the returned absolute `Dockerfile.readiness` path, record the immutable image ID, and run it with `--network none --read-only --tmpfs /tmp:rw,exec,size=1g`, mounting only a new evidence directory at `/evidence`. Set `READINESS_NETWORK_NONE=1` and `READINESS_IMAGE_ID` to that identity, then execute `python scripts/verify_readiness.py restore --output /evidence/restore.json`. The environment marker is a guard against accidental invocation, not a substitute for Docker network isolation. Never mount a live database or HOME. Exact executed commands are in the command receipts.
